## 这份技能解决什么

系统级目标（"做一个财务系统"）直接问模型要需求，拿到的永远是 5~14 条骨架：
登录、计费、导出、测试……看起来齐全，实际上一个模块只有一条，等于没拆。

真实团队在这一步会花半小时到一小时：逐模块过一遍业务流、数据、接口、权限、异常、
迁移、运维七个视角，边讨论边补。**这份技能就是把那半小时结构化**，让一个人也能做出
同等密度的需求集。

## 形态：一棵树，不是一张清单

**一次性列 45 条 = 广度优先展开一层，人不是这么干的。** 人是递归下降，每层只回答一个小问题：

    多租户财务中台                      L0 系统
    ├─ 计费与费率                       L1 域
    │  ├─ 费率模型与版本管理             L2 能力
    │  │  ├─ 费率生效时间与历史回溯      L3 可执行条目 (1~3 人天)
    │  │  ├─ 阶梯/按量/固定三种计费类型
    │  │  └─ 费率变更的审计与回滚
    │  └─ 计费引擎与账期
    └─ 对账与差异处置

工具是 `team_decompose`，**一次调用只展开一个节点**。第一次不传 parentId（切顶层的域），
之后对每个 branch 各调一次。

### 什么时候可以收成叶子（局部判据，三条全中才算）

1. **estimateDays ≤ 3** —— 一个人 1~3 天做得完。超了说明它还是个"能力"，不是任务。
2. **有客观 acceptance** —— 写不出判据说明你还没想清楚它是什么。
3. **单一职责** —— 标题里没有"和／及／与／、／+"连接的两件事。有就至少还能拆成两条。

少一条就标 `kind: 'branch'`，下一轮再拆它。**判据是局部的**：你每次只回答"这条我一个人
3 天做得完吗"，答不上来就继续拆。所以规模是**涌现**出来的，不是凑出来的 ——
租户管理可能 L2 就到底，总账对账会一路拆到 L4。

### 拆错了就删，不要"收成叶子"

发现某个节点是空占位、跟别的域重复、或者当初切错了 → `team_prune({nodeId, reason})`。

**别拿 `closeAsLeaf` 处理垃圾节点**：那是给"这一块本来就够小"用的，它现在也要过叶子判据
（人天 + 验收 + 单一职责）。

> 实测教训：模型曾把一个空占位节点用 closeAsLeaf 收掉，理由写的是「占位节点，无任何实际
> 拆分内容」—— 结果树上多了一个假任务，还被某个成员真的领走了。

### 还有一条：一个分支底下不许一口气摊出 >10 人天的叶子串

那说明中间缺了一层。先把它拆成 2~4 个**能力组**（`kind:'branch'`，每组 ≤10 人天，
按业务子流程 / 数据边界分，**不是**按"第一批第二批"分），再逐组展开成叶子。

> 实测教训：判据只管叶子够不够小时，模型会「域 → 叶子」一步到底 —— 45 个叶子全合规，
> 但树只有 2 层，每个域挂着 5 条 12 人天的活。中间这层是真实团队里
> **"一个负责人一个迭代吃得下的一块"**，少了它排期和分工都落不到人头上。

> 为什么不用全局条数当判据：试过，每域下限设 3 就每域给 3 条，设 5 就整整齐齐每域 5 条。
> 全局阈值对模型是**目标线**不是下限。局部判据没有线可卡。

## 编制：人数从规模推，不是套模板

`team_roster` 会按**人均叶子数**判：一个人手上 **2~15 条**才算一摊正经活，上限 **20 人**。

- 人均不到 2 条 → 人分多了。每个 agent 都要读上下文、对契约、汇报，协调成本比干活还高。
- 人均超过 15 条 → 人太少了。他一个人串着跑，而批内并行是这套调度的全部意义。
- **按能力边界切人**，不是每个域硬配一个人 —— 领地天然连在一起的（存储 + 持久化）合成一摊。

> 实测教训（2026-08-16）：老版本编制写死 2~6 人，跟需求规模完全脱钩，两头都错 ——
> 200 个叶子照样只给 6 人（每人 33 条串行跑死），7 个叶子给 6 人（每人 1 条，纯协调开销）。
> 200 个需求也不该排 50 个 agent：真实团队就是一二十人，再多主脑自己成瓶颈。

## 过程要留痕：开会

真实团队的结论是开会开出来的，而"为什么这么定"往往比结论本身更值钱。关键讨论用
`team_meeting` 记下来（`kind`: requirements 需求评审 / design 开发研讨 / test 测试研讨 /
review 复盘），notes 里每条是**某个成员用自己的视角说的话**，decisions 是会上定下来的
跨域契约与口径。

三场不能少（`team_claim` 会挡）：
- **开发研讨会** `design`：接口契约、数据边界、谁的改动会碰到谁 —— 跨域契约定不清，实现阶段必打架。
- **测试研讨会** `test`：验收口径怎么算过、哪些边界必须有用例 —— 不然"做完了"各说各话。
- **工期复核会** `estimate`：每个人对着自己那摊活说实话。**按业务语义难度加权，不是按条数** ——
  借贷平衡、期末结转、对账容差、并发幂等这些地方要往上抬。

> 实测教训：上一版方案里总账 6 条给了 9 天、对账 5 条给了 8 天，而平台基建给了 22 天。
> 财务系统里最难的恰恰是账务语义，按条数估必然乐观。

## 依赖：顺序要机器可读

**每个叶子都必须给 `dependsOn`**：有硬前置就列 id（拿不到它的接口/表结构就没法开工），
确认没有就给 `[]`。缺这个字段会被打回 —— 空数组是"我确认无前置"，缺字段是"我没想过顺序"。

> 实测教训：77 个叶子 dependsOn 全空，而会议决议的散文里明明写着
> `M1初始迁移 → M2(RLS/组织)+M4(记账引擎) → M3(审批衔接)`。顺序只活在人话里，
> 执行层没法算施工序，并行派兵必然打架。

闭环时会自动算：
- **施工批次**：批内可并行（领地已互斥），跨批必须串行 —— 执行层照这个派兵。
- **跨人依赖**：谁在等谁的哪一条 —— 讲方案时必须说清。
- **成环直接打回**。拆环的标准做法是**契约先行**：把一条切成"先给接口契约/表结构"和
  "再落实现"两步，让别人只依赖前半步。

## 产出标准（不达标就是没做完）

- **没有未展开的 branch**（工具回执里的 `openBranches` 必须归零）。
- 每个叶子可被**一个人独立负责、独立验收**，≤3 人天。
- 覆盖必须完整：只写"能跑通"的正路 = 没做需求分析。
- 一份给人读的需求文档落到工作区（不是条目的复制粘贴，是能拿去对齐的文档）。

## 方法：先分域，再对每个节点过七视角

### 第一步 · 分域

按**子系统 / 能力域**切，不按技术分层切（不要"前端/后端/数据库"这种切法）。
常见域：身份与权限、核心业务流、计费与账务、单据与审批、报表与导出、
对账与流水、集成与开放接口、数据模型与迁移、可观测与运维、配置与租户。
**具体域由目标本身决定** —— 上面只是常见形状，不要照抄。

### 第二步 · 每个域过这七个视角

对**每一个域**逐条自问，每问出一件事就是一条需求：

1. **业务流**：正常路径分几步？每一步谁触发、产生什么状态流转？
2. **数据**：要存哪些实体？关键字段、唯一约束、状态机取值？历史数据怎么迁移？
3. **接口**：对内/对外暴露什么？入参校验、幂等、分页、错误码？
4. **权限**：谁能做这件事？越权怎么处理？数据级隔离（只能看自己的）怎么落？
5. **异常与边界**：并发、重复提交、部分失败、超时、金额精度、时区、空数据？
6. **验收**：怎么证明它做完了？（可执行的判据：用例/命令/数值，不是"功能正常"）
7. **运维**：出问题怎么发现？关键指标、日志、告警、回滚路径？

七个视角不是每个节点都必然产出 7 条，但**一个节点只产出 1 条 = 没过这七个视角**。
往下每一层都过一遍这七问 —— L1 问的是"这个域包含哪些能力"，L2 问的是"这个能力落到
哪些数据、接口、异常路径"，问题相同，粒度递减。

### 第三步 · 并行深挖（分支多的时候）

同一层的兄弟节点互不相干 → 并行派只读子 agent，一支一个。

⚠️ **每个 agent 只带自己那一支的祖先链**（L0→L1→L2），不要把另外八个域的细节塞给它。
人也不会一边想费率一边想导出 —— 上下文隔离才可能真的想深。

    agent({ type: 'research', description: '<域名> 需求深挖',
            task: '针对「<域名>」域，按业务流/数据/接口/权限/异常/验收/运维七视角逐条列出需求。
                   每条给: 一句话标题 + 展开说明 + 客观验收判据 + 依赖的其它需求。
                   只读代码不许改文件。回一个 JSON 数组。' })

主 agent 负责合并、去重、编号、定优先级和依赖 —— **合并这一步不能外包**，
它决定了需求集的一致性。

⚠️ **合并 ≠ 重写。** 子 agent 挖出来的 detail 和 acceptance **原样带回**，你只做四件事：
去重、统一编号、串 dependsOn、定优先级。不要"顺手精简一下"——

> 实测教训（2026-08-16）：两个子 agent 各挖回 12k 字、每条 detail 200~500 字带接口签名、
> 错误码和 `node --test` 断言；主 agent 转述一遍后登记进去的 detail 中位数只剩 166 字，
> 一半条目连函数签名都没了。条数没变，深度全丢。领需求的人照着这种骨架做不出东西。

detail 太短会被 `team_requirements` 直接打回（`THIN_DETAIL`）。一条 detail 要能回答：
**数据长什么样 / 接口签名与返回 / 错误码 / 边界与异常**。

### 第四步 · 定优先级与依赖

- P0 = 缺了系统就不成立；P1 = 该有，缺了能交付但残缺；P2 = 增强。
- dependsOn 只写**硬依赖**（A 没完成 B 根本没法开工）。依赖链要能看出施工顺序。

## 落文档

写一份给人读的需求文档到工作区（如 `<项目>/REQUIREMENTS.md`），结构：

    # <系统名> 需求说明
    ## 1 背景与目标        —— 为什么做、做成什么样算成功
    ## 2 范围与非目标      —— 明确不做什么 (非目标和目标一样重要)
    ## 3 领域划分          —— 每个域一句话职责 + 域之间的边界
    ## 4 需求明细          —— 按域分节, 每条: 编号 / 标题 / 说明 / 验收 / 优先级 / 依赖
    ## 5 数据模型          —— 关键实体与关系
    ## 6 风险与未决        —— 需要用户拍板的决策项
    ## 7 里程碑            —— 交付批次

然后调 `team_requirements({ documentPath, requirements: [...] })` 把文档路径和结构化条目
一起登记 —— 文档给人对齐，条目给机器分配，两者缺一不可。

## 自检清单

调 team_requirements 之前逐条核对：

- [ ] 域 ≥ 5 个，每个域 ≥ 3 条需求
- [ ] 每条都有客观验收判据（能被执行或观测，不是"正常工作"）
- [ ] 权限、异常边界、数据迁移、可观测 这四类**各至少有一条**（最常漏的四块）
- [ ] 依赖关系写清了，能据此排出施工顺序
- [ ] 文档已落盘，不是只在对话里说过
