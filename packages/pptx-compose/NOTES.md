# 一 · 先跑这个

```bash
cd packages/pptx-compose
npm run check      # build + verify-render + audit-style-drift
```

- `scripts/verify-render.mjs` —— 20 模板 × 4 风格零重叠 · 图表 10 种边界数据 ·
  导出 XML 的结构不变量 · 字体 metrics · 对比度 · 10 种极端输入
- `scripts/audit-style-drift.mjs` —— 模板里有没有绕过主题写死的颜色
- verify 第 8 节 —— **导出 pptx 的结构合法性**: rels 完整性 / content-types 覆盖 /
  shape id 不重复且非 0 / `p:transition` 排在 `clrMapOvr` 之后 / sldId 能解析。
  排版问题看图能发现, **结构问题看不出来**: LibreOffice 容忍很多不合规的东西,
  PowerPoint 直接拒绝打开 (transition 那条就栽过一次)。
- `scripts/text-metrics-fixture.json` —— LibreOffice 实测的文本宽度基准
  (5 组中英字体配对 × 10 类脚本组合)。verify 第 7 节拿它守 measureText 的精度,
  **不需要装 LibreOffice**。字体或烘焙 metrics 变了才需要重生成 (方法见文件头)。

**它判不了"好不好看"。** 排版必须导出 PDF 逐页看:

```bash
soffice --headless --convert-to pdf --outdir out deck.pptx
pdftoppm -png -r 60 out/deck.pdf out/p        # 再拼 contact sheet
```

预览端 (右侧面板看到的) 是**另一套渲染代码**, 要单独截:

```bash
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless \
  --screenshot=pv.png --window-size=1280,720 file://$PWD/pv.html
```

# 二 · 反复踩到的八类坑


### 1. 能力写完了, 但调用方看不见它
一晚上命中五次: 三层配方 (20 个模板没人调用) / 折线图 (schema 里没有 'line') /
`LayoutParams.bleed` (定义了没人读) / `StyleSpec.motion` (四套风格都填了值) /
`pageNumber` (SKILL.md 写了 20 次, 零实现)。

**做完一个能力, 回头 grep 一遍谁真的读它。** 查法: 把对外文档 (SKILL.md / tool
schema) 里提到的每个字段, 逐个去实现里 grep。

### 2. 同一个语义两条实现, 只修了一条
`rgba` 直塞 `hexNoHash` 这个坑 2026-07 修过形状填充, 文字 run 就在下面几十行却漏了,
又活一个月。`objectFit` 只有预览实现、渐变 custom path 只有导出实现。

最阴险的一种: 两边**都读了同一个字段**, 但 CSS 的语义和 OOXML 不一样。
行高就是: `<a:lnSpc><a:spcPts>` 是钉死值, 而 CSS 只在段落上写 `line-height`
不写 `font-size` 时, 这个块的 **strut** 会用继承来的默认 16px 字体去算半行距,
行盒被撑高约 20px。看起来"两边都实现了", 实际差 22%。

还有一种: **兜底值把外层的设定盖掉**。段落没有显式 align 时曾经硬写
`text-align:left` —— 表格单元格的对齐写在 `<td>` 上, 里面的段落再写一个 left
就把它盖没了 (导出三列各就各位, 预览全左对齐)。**没有值就别写, 让它继承。**

**预览 (`renderer/slide-html.ts`) 和导出 (`exporter/writeSlide.ts`) 是两套代码。**
任何视觉属性都要两边都验。快速查法: 同一个属性名在两个文件里 `grep -c`,
`0 vs 12` 就是没实现。

### 3. 写死一个数, 不看给它的空间
柱高 `ratio * 320` / 表格行高 44px / 面板标题 36pt / 数字 140pt / 章节页的
`padding.top: 380`。每一次都是"调用方算好的空间被扔掉", 或者"这个值对短内容对、
对长内容就崩"。

看到字面量尺寸先怀疑。要按容器反解就用 `titleSizeForBox()`;
串联多个元素**绝不能各自写死 y**, 用一个 VStack 从单一锚点往下排。

### 3b. 给"文字要占的位置"留空间, 不只是给图形
柱状图的刻度顶原来只保证**柱子**放得下 (极值正好等于刻度端点时加一档)。
但柱顶还要画数值标签 —— 实拍 max=770 / 顶刻度 800: 柱子放得下, 中间只剩 ~11px,
而标签有 24px, 被顶部网格线横穿。
改成按**轴跨度比例**要求净空 (LABEL_HEADROOM = 0.11 ≈ 一行标签), 不够就再加一档。
只有画标签的单系列需要 —— 多系列不画标签, 平白加一档会让柱子变矮。

### 3c. 容器装不下自己的内容 → 表现是"字莫名其妙变小"
`bleedBandFrame` 以前只能传"色带多高", 但可用高度是
`height - skew - padTop - 20`, 而 **skew 是每套风格各不相同的比例**
(chevron 0.22h · ribbon 0.18h · capsule 0.30h · line 0)。调用方不可能知道 skew ——
featureGrid 传 210, 在 chevron 下只剩 98px, 而内容要 133px,
于是求解器把整块压到 **0.72**: 标题 36→25.9pt, kicker 14→**10.1pt**,
而且四套风格压的档位还各不相同。

这类 bug 极难查, 因为它**不报错也不溢出**, 只是字小了一圈。
判法: 把导出的 `sz=` 全列出来, 和模板声明的值对一下 —— 对不上就是被缩了。
现在改成传 `contentHeight` (调用方知道自己有多少内容), 由 bleedBandFrame 按各风格
的斜切比例反解色带高度。

### 4. 图形在陈述一个假事实
`Math.max(0, value)` 把负数画成零柱; 缺失数据补 0 画成"降到 0"; 真零和缺失长得一样;
特性网格给同类项配不同形状 (暗示存在不存在的区别)。

**装饰可以无意义, 但不能传达错误的意义。** 对用户数据做 clamp/截断时问一句:
这是保护还是篡改?

### 5. 半透明只对"面"成立, 对**文字**不成立
文字 run 上的 `<a:alpha>` 三个渲染器三种结果: LibreOffice **吃掉行尾字符**
(英文 label "…fault isolation" 画成 "…isolati"; 中文只吃最后一个字, 所以藏了很久),
Keynote **直接忽略**, 预览端按 CSS 正常画。而且对比度守卫算的是那个实色,
和实际画出去的不是一个颜色。

深底上要柔化白字, 用 `softInk(alpha)` 跟底色**预先合成实色**。
`withAlpha` 留给形状填充 —— 那条路上 alpha 是通的。
`verify-render` 第 3 节现在守着"文字 run 不许带 `<a:alpha>`"。

### 5b. 照片上的文字: 底色不可知, 只能靠遮罩给下界
"遮罩之后大概是 #1A1A1A" 这种**假设**站不住 —— 0.55 的黑压在亮照片上实测是
[69,105,26] 的中绿, 深红 kicker 对比度只有 **1.70**。

更要命的是遮罩**根本没盖住文字**: 硬边色带从 y=360 开始, 而文字块从 y=287 开始,
kicker 整行在遮罩之外。之前量到"底色很暗"只是那张照片那块恰好是阴影。

正确做法两条:
1. 遮罩要**覆盖整个文字块**, 并且是真渐变 (硬边一眼像"贴了块布")。
2. 遮罩强度给出**可以证明的下界**: 0.55 之后任何照片最亮不过 0.45×255 ≈ 115,
   白字对比度恒 ≥ 4.77 (AA)。所以照片上的小字一律走 onInk, 不要挑 accent。
   记号 (纯色形状) 可以保留 accent —— 它靠色相就能读出来, 不吃亮度对比。

### 6. 颜色"选了"不等于"看得见"
深红 accent 写在深棕 ink 上对比度不到 1.5, 整行字消失 —— overlap 断言抓不到,
求解器也不管颜色。已在四个地方栽过。

深底上的 accent 一律过 `readableAccent()`;
主题色本身也要达标 (`verify-render` 第 5 节守着 muted/ink/onInk ≥ 4.5)。
**别靠看图判断"暗不暗", 直接算对比度。**

# 三 · 两端一致性: 单位与约定 (逐项实测过)

## ⚠️ OOXML 的百分比单位: 千分之一个百分点

`<a:gs pos>` / `<a:alpha val>` / `<a:lum bright>` / roundRect 的 `adj` ——
这些全是 **0~100000**, 不是 0~1000, 也不是 0~1。
渐变停靠点曾经乘 1000 → 三档全挤在前 **1%** 里, 剩下 99% 是最后一档的纯色,
"三档渐变"实际画出来是**平涂**, 而且一直没人发现 (平涂也挺好看)。

**查法: 取四个角的像素比一比 —— 两端都要取。** 四角同色 = 渐变没生效。
预览端犯的是同一个错 (`${s.pos}%` 而 pos 是 0~1), 而且**预览自己的两条渐变路径
互相不一致**: custGeom 走 SVG 写的是 `pos * 100` (对), 普通 rect 走 CSS 的写的是
`pos` (错)。

角度约定三家都不同, 换算记牢:
· OOXML `ang` 从**正东**顺时针 (1/60000 度)
· CSS `linear-gradient` 从**正北**顺时针 → **CSS = OOXML + 90**
· SVG 的 y 轴向下, 和 OOXML 一致 → 方向向量直接 (cosθ, sinθ), 不要减 90
修好之后左上 [13,20,36] / 左下 = t.ink / 右上右下朝 accent 抬 —— 和代码注释
描述的一致。顺带把封面 kicker 的实测对比度从 3.93~4.31 拉回 4.75~5.29。

## 效果 (阴影/内阴影/发光): 单位是 EMU, 别再除 12700

预览端的 `scale` 已经是 **px/EMU**, 而 effects 的 blur/distance 在模型里就是 EMU
(原样写进 OOXML 的 blurRad/dist)。之前又除了一次 12700 (那是 EMU/**pt**),
两次换算下来所有 box-shadow 都是 `0.0px 0.0px 0.0px` —— 等于没画,
而看图完全看不出来 (阴影本来就淡)。**判这类事直接把生成的 CSS 打出来。**

`innerShadow` 就是 `box-shadow: inset`, `glow` 是零偏移 + spread ——
以前注释说"CSS 里没有等价物"是错的。真正没有干净等价物的只有 `softEdge`(要 mask)。

**LibreOffice 不渲染 `<a:innerShdw>`** (outerShdw / glow 都渲染)。
XML 是对的, PowerPoint 认。Quick Look 对 effects 一律不渲染, 在这件事上不是有效裁判。

## custGeom 的描边: 必须 non-scaling-stroke

`stroke-width` 的单位是 **viewBox 单位**, 不是 px 也不是 pt。而我们的 custGeom
用 `preserveAspectRatio="none"` 拉伸, **x/y 缩放比不同** —— 直接给数字的话
横边和竖边会粗细不一样。实测一个 viewBox 100×100 画成 400×200 的方框, 声明 3px:
预览横边 4px / 竖边 8px, 而导出两边都是 3px。

加 `vector-effect="non-scaling-stroke"` 后 stroke-width 回到**屏幕像素**,
直接给 `widthEmu * scale` 就对了 (实测 2/2/6/6, 和导出一致)。

**整页像素差在这件事上完全不动** (描边只占极少像素) —— 判描边要直接量线宽。

## custGeom 的 strokeOnly

`customPath.strokeOnly` 意思是"只描边不填充"。预览端曾经**一次都没读过**它 ——
声明了 strokeOnly 的形状在预览里被实心填掉。
heroBackdropLayers 的线稿层正好传的是**透明填充**, 所以一直看着没事;
只要有人给它一个真填充色, 两端立刻不一样。已修。

## 圆角: 传 cornerRadius 就够了 (2026-08-10 起)

以前 `cornerRadius` 只在 `geometry: 'roundRect'` 时才生效, 而调用方几乎都传
`'rect' + cornerRadius` —— 于是 KPI 卡、图表柱顶、featureGrid 图标的圆角
**两个渲染器都静默忽略**, 一直画的是直角 (实测 KPI 页导出 18 个 prst="rect"、
零个 roundRect)。现在 builder 会自动提升成 roundRect, 一处改完两端都对。

roundRect 的 `adj` 是"圆角半径占较短边的比例", 合法范围 **0~50000**, 必须钳位 ——
图表的零值桩只有 3px 高而柱子 cornerRadius 是 4px, 不钳位算出来是 133333。

## 图片滤镜: 两端已对齐 (2026-08-10 量过)

四种滤镜 (grayscale / duotone / biLevel / lum) 在 LibreOffice 里都真的渲染,
预览端也已对齐。**别再用 CSS 的 `brightness()` 去实现 `<a:lum bright>`** ——
前者是乘性、后者是加性, 实测差一倍多 (原图亮度 112: 导出 74.5 = 112−0.15×255,
CSS 92 = 112×0.85)。预览走一条 SVG feComponentTransfer 精确表达:

```
out = in×(1+contrast) + (0.5 − 0.5×(1+contrast) + brightness)
duotone = 先 saturate(0), 再 tableValues 把 0~1 映到 dark→light
```

判滤镜对不对**别看缩略图** —— 量区域的平均亮度和平均饱和度, 一次就看出
"duotone 把颜色全丢了"(饱和度 0 vs 30)。

**已知不支持**: 图片圆角。`LayoutParams.cornerRadius` 只在**缺图占位**那条分支
生效, 真图走 `images.add` 而它没有这个字段 —— 有图直角、缺图圆角。
目前没有模板用它; 要用得先给 PictureShape 加 roundRect 几何。

## maxLines 现在是真的了

`LayoutParams.maxLines` 曾经**只影响测量不影响输出** (压低测出的高度, 全文照画,
反而更容易溢出)。现在 paint 会真截断并补省略号。

截断走 `truncateToLines`, 它是对 `measureText` 做二分 —— **刻意不自己再断一次行**:
断行规则 (CJK 逐字 + kinsoku + Latin 按词) 只能有一个来源, 两处各写一遍会出现
"测量说 3 行、截断按 4 行截"的错位, 比不截更难查。

截断发生在 paint, 也就是**模型层**, 所以预览和导出拿到的是同一份文本 ——
不会出现两个渲染器截得不一样。

## 文字的 vAlign: compose 侧刻意不用

`vAlign`(bodyPr anchor) 在**表格单元格**上两端都正常, 那是它真正要紧的地方。
独立文本框的 vAlign compose 传不了 —— 但 compose 的垂直定位走 VStack 的
`justify`, 那才是这套引擎的正规做法, **不是缺口**。

# 四 · 怎么验 (工具会骗人, 挑对仪器)

## ⚠️ 验 XML 要用**真解析器**, 正则查不出非法字符

2026-08-10: 一份对抗性文本 deck 里 **3 页导出的是非法 XML**, 而当时的结构检查
(全是正则) 全绿 —— 正则不在乎字符合不合法。换 `xml.dom.minidom` 一解析就现原形。

根因: `esc()` 只做了 5 个字符的转义, **控制字符原样穿过去**。
XML 1.0 里 `\x00-\x08 \x0B \x0C \x0E-\x1F` 是**彻底非法**的 ——
不是"要转义", 是连 `&#7;` 这种数字实体也不合法, **唯一正确的处理是剔除**。
而这类字符在从 PDF / 终端 / CSV 复制来的文本里非常常见, 一个就够让整份 pptx
**任何工具都打不开**。

实测确认**转义本身一直是对的**: `&` `<` `>` 都正确, 连
`</a:t></a:r><a:r><a:t>INJECTED` 这种注入尝试也是作为字面文本显示的。
emoji / 数学粗体 / 扩展汉字 / 阿拉伯文都是合法字符, **不能被误删**。
verify 第 8 节现在拿对抗性文本跑一遍并断言这三件事。

## ⚠️ LibreOffice 会骗你

看图验证全走 `soffice → pdftoppm`, 但 LO 自己有渲染 bug —— 上面第 5 类就是
**先怀疑自己、差点去改一个没坏的页面**才查出来的。判断"这是我们的 bug 还是
渲染器的 bug", 拿第二个引擎对一下:

```bash
qlmanage -t -s 1600 -o out deck.pptx     # macOS Quick Look = Keynote 引擎
```

两边都错才是我们的错; 只有一边错, 先去看导出的 XML 对不对。

## 逐页像素比对: **先统一分辨率**

PIL 的 `ImageChops.difference` 对尺寸不同的两张图不会报错, 而是按较小的那张裁剪
对比 —— 一张 r=60 (801×450) 和一张 r=96 (1281×720) 比出来是 **37.94% 的假差异**,
看上去像"版面被改坏了"。2026-08-10 因此白查了一轮。
**比之前一律 `.resize((1280,720))`**, 或者先断言尺寸相等。

## ⚠️ 图片这条路: 测试必须用**真图**

2026-08-10 之前所有测试都传 `null` 走占位符 —— 于是"图片被拉伸变形"这个
**每张图都中招**的 bug 藏了很久。造测试图的诀窍: 画一个**正圆**(变形一眼可见)
加一圈**红边框**(裁没裁、裁了哪两边一眼可见), 再配几种极端比例
(1600×600 / 600×1600 / 正方 / 160×120)。

`fit:'cover'` 的裁剪 (srcRect) 补在 **exporter 的 prefetchImageSources 之后** ——
那是唯一一个"所有来源 (本地路径 / http / blob) 都已经内联成 data URL"的时刻,
一次覆盖全部形态。compose 侧只认 data URL, 传本地路径探不到尺寸, 会静默不裁。

## 风格差异是可以量的

明康最早的抱怨是四套风格"换汤不换药"。判断这件事别靠看图 —— 把同一份内容渲染成
四套风格, 逐页比**边缘图的 Jaccard 距离** (只比结构, 与配色无关), 一次就排出序:

```
封面 69% · 宣言 71% · 章节 65%   ← 形态语言足
图表 15% · 数字 23% · 三栏 18%   ← 结构本来就该像 (柱子就是柱子)
```

2026-08-10 用它抓到一件事: 形态语言铺到了 20 个模板里的 **15 个**,
漏掉的 5 个 (chart / contrast / numbers / photoSpread / quote) 恰恰是四套风格
之间最难分辨的几页 —— 不是巧合。

**但别为了拉高这个数去加花样。** 三栏/表格/KPI 分数低是因为栏和行本来就不该变形,
它们早就有 dividerMotif 了。真正该补的判据是**一致性**: 同一份 deck 里,
标题到内容的过渡、分隔符、帽条, 处处应该是同一个记号。
图表里的柱子/网格/零线**不算装饰**, 那是数据, 不能碰。

## 文本测量的实测精度 (2026-08-10 标定)

| 内容 | 误差 (预测 vs LibreOffice 实测) |
|---|---|
| 纯中文 / 纯拉丁 | ±1.5% 以内 |
| 中英混排 | **稳定偏宽 5~11%** |
| `AV` `To` 这类 kern pair | 最高 +11.2% (LO 应用字偶距, hmtx 表里没有) |
| 最危险的一侧 | -0.1% (在 WRAP_SAFETY_PX 的 2px 安全边内) |

**偏宽这部分刻意不修。** 两个方向的性质完全不同: 偏窄 → 真溢出;
偏宽 → 提前折行 + `titleSizeForBox` 反解的字号偏小, 只是浪费。
去修偏宽会把误差推到偏窄那一侧, 那才是真问题。
中英混排的偏差来自 CJK↔拉丁**边界** —— 和大小写、空格都无关
(全小写无空格的 "算力gpu数据rag" 照样偏 +5.9%)。

## 多系列配色: 两条硬指标, 且**验证脚本要真的调它**

· 相邻两色对比度 ≥ **2.0** (2026-08-10 从 1.35 提上来)
· 每个系列色 vs 纸底 ≥ 1.6

1.35 那个门槛让 minimal-line 的 2 系列"合规地"糊着 (实测 1.44):
`#8B0000` 再朝 ink 压 0.58 得到 `#53120f` —— **暗色没有下压空间**。
分组柱还能靠位置分开, **两条折线叠在一起就是一条**。

固定系数解决不了这个 (一刀切翻向会让别的主题变差), 所以改成**保证指标**:
默认系数达标就照用 (三套主题一个字节不变), 不达标才两个方向一起扫,
在满足门槛的候选里挑**离已用颜色最远**的 (只看相邻会让第 1 和第 3 撞车)。

代价要知道: minimal-line 的第二色是淡玫瑰, vs 纸底 **1.66**, 贴近下限 ——
单色相配色的必然取舍。要更强的区分只能引入别的色相, 那会破坏"整份 deck 一个色系"。

`__seriesPaletteAudit` 这个函数一直在, 但**以前没人调它** ——
当初调系数时临时跑过一次就没接线。现在 verify 第 5 节四套风格 × 2~6 系列都查。

## 页脚取色: slideChrome 自己采样, 别让作者去记页型

deck 工具会**自动**调 slideChrome 并按页型传 `onDark` (它维护了一张"深色面板在左"
的表), 而 SKILL 主推的 **deck.mjs 要作者自己调, 示例里没有 onDark** ——
于是 bulletList 这种左深页型的页脚实测只有 **2.14**。让作者去记哪些页型深色在左
是不合理的, 两条路的产出也不该不一样。

现在 slideChrome **自己采样**左下角的实际底色 (它是在模板画完之后调的, 底已经在了),
再交给 `readableAccent(ground, muted)` 保证 ≥4.5。`onDark` 保留为显式覆盖。

**但页码那侧不能采样** —— 右侧多是斜切面板, 形状的**包围盒会覆盖它的路径并不覆盖
的点**, bbox 采样在那里不可靠 (照采样改过一版, 页码反而从 4.52 掉到 2.58)。
左下角是矩形面板, 采样才成立。原设计"页码永远在浅底 → 一律 muted"是对的。

## agent 传错类型时: 要么讲清楚, 要么别静默画白

2026-08-10 用 15 种"传错类型"的用例压了一遍, **9 种直接抛异常**, 而且几乎都是
同一条毫无信息量的消息 `text.split is not a function` —— 那个 split 在
measureText 深处, **完全不说是哪个槽位错了**, agent 拿到没法自愈。

`Text()` 是所有模板的唯一入口, 在那里规范化, 判据是"调用方的意图清不清楚":
· number / boolean → 转字符串 (`title: 42` 意图明确)
· null / undefined → 空串 (缺个 label 不该让整页崩掉)
· 对象 / 数组 → **明确报错**并打出拿到的东西 (渲染成 "[object Object]" 是静默画坏)
9 个崩溃降到 3 个, 剩下的报错能指出问题。

另一半是**静默的空白页**: `cards: []` / `columns` 传了字符串数组 / `steps` 缺 label
都不报错, 就是安静地出一页空白。deck 工具那层的 `missingSlots` 已经拦了空数组,
但**直接调模板的 deck.mjs 是文档主推的路**, 它绕过那层。
所以 `render()` 里加了判据: **内容型**调用 (assertNoOverlap !== false) 如果一个
内容叶子都没画出来就出声 —— 背景层/骨架那些调用用的正是 assertNoOverlap:false,
不会误报 (实测中英各 18 页零告警)。

## 两个断言, 管的是两件事

- `assertNoOverlap` —— 两块内容**叠**没叠 (IoU > 5%)
- `assertWithinCanvas` —— 内容有没有画到**版面外**

以前只有前一个, 于是"内容跑到页面下边缘之外"一条都抓不到, 全靠人肉解 pptx 数
`<a:off>/<a:ext>`。两个都只看**内容**叶子 (text / image / table):
装饰形状出血是设计手段 —— 封面和章节页的背景层刻意超出版面 180px,
那是 `heroBackdropLayers` 的整个用意。要让某个内容节点也合法出血, 声明 `bleed`
(两个断言共用这个字段)。

比的是**版面**不是 render 的 bounds: 画出 bounds 但仍在版面内是合法的
(多次 render 叠层就这么用), 画出版面才是真的看不见。

# 五 · 设计约束与已知差异

## 几个不显然的设计约束

- 模板里不许出现任何**语言相关的词**。图表单位曾经写死 `单位: ${unit}`,
  纯英文 deck 里就冒出两个中文字; 引擎不知道 deck 是什么语言, 也不该猜 ——
  改成 `(min)` 这种中英通用的写法, 语言依赖直接消失。
- `Spacer` 现在是真的了 (默认 flex:1 吃掉主轴剩余空间, `minLength` 是最低尺寸)。
  它以前是**空操作** —— 工厂不给 flex、measure 返回 0×0, 而 DSL 示例和三个模板的
  注释都写着"推内容到底"。实现它会让原本依赖它"不干活"的版面变样, 所以
  **实现一个空操作之后必须回头看所有调用点**: manifesto 变好了 (宣言居中/署名压底),
  heroImageQuote 变差了 (署名被顶到版底、和引言脱开) —— 那处直接去掉。
- **显式尺寸 + padding 必须两处一起算。** measureLeaf 把 padding 加进 preferred size,
  layout 拿到 assigned 后再按 padding 缩回去 —— 两边必须是同一个数。
  交叉轴上曾经直接用裸的 explicit: 8px 的圆点带 padding.top:12 → 分到 8 再减 12
  = **-4**, paintShape 见负数直接 return, 元素凭空消失。
  (a7c6cee8d 修的是 measure 那半, 2026-08-10 这次是 layout 那半 —— 一个坑的两半。)
- `align` 是"我怎么摆我的孩子", `alignSelf` 才是"我自己怎么被摆" —— 混用会让
  卡片不吃高度、柱状图基线不齐。
- **Grid 不把剩余高度分给行**, stack 的 flex 会。要撑满就别用 Grid;
  反过来文字格子用 Grid 才对 (撑满会把文字拉散)。
- `<p:transition>` 必须排在 `clrMapOvr` 之后 —— 放错 PowerPoint **拒绝打开**文件,
  不是忽略。
- `singleLine` 现在会写 `wrap="none"`。所以大字号溢出不再表现为折行, 而是**横向
  溢出**, 两种断言都抓不到 —— 单行大字的字号必须由容器宽度反解。
- 换页动画挂在 `render()` 而不是 deck 工具里: `render()` 是 20 个模板的唯一咽喉,
  两条使用路径 (deck 工具 / SKILL 里的 deck.mjs 直调) 才都能拿到。
- 页码由 deck 序号推导, 不让模型手写 (增删页会错位); 封面和章节页不编号。

## 已知且可接受的差异

- 预览用浏览器断行, 导出用自研 font metrics —— 个别文本预览会多折一行。**导出为准**,
  别当成新 bug。整份 deck 逐页像素比对下来平均差 2.7~2.8%, 基本全是栅格化差异;
  超过这个量级就该去查, 不是噪声。
- Kaiti/Yuanti 的 Bold 面没匹配上 OS/2 weightClass, 退回 Regular metrics。
  中文全角等宽, 测量不受影响。

## ⚠️ renderer 里有一套同名的老模板

`@openneox/pptx-renderer` 导出了 `coverHero / timeline / kpiCards …` **同名**的
20 个老模板 (坐标数学版), 和 compose 这套完全是两回事: 扁平色块、时间轴只有一根线
加小圆点 —— 就是用户抱怨过的"光板"。签名也不同: 老的是 `tpl(ppt, slots)`,
compose 是 `tpl(slide, slots)`。

**写 deck.mjs 时模板一律从 `$NEOX_PPTX_COMPOSE_LIB` 导入。**
SKILL.md 的代码模板曾经从 `$NEOX_PPTX_LIB` 导入模板 (2026-08-10 已修) ——
那等于文档主路径绕过了整个 compose 引擎。

**仍未处理**: `create_slides` 工具 (≤5 页快捷口) 用的是 renderer 的
`TEMPLATE_BUILDERS`, 也就是老模板。它自己的描述已经劝退真实 deck ("6+ 页别用"),
但 3 页的小 deck 仍会拿到老版观感。换成 compose 需要处理签名和风格选择的差异,
不是纯文档改动。

## 还没做的 (需要拍板)

1. **配图分流 ImageryPolicy** (abstract→生成 / concrete→搜索 / decorative→画) ——
   要接外部图片生成或搜索能力, 涉及成本和服务选型。
2. **模板画布参数化** —— 模板里写死 1280×720 共 53 处。做完才能支持 4:3 / 1920×1080。
   工作量不小且必须逐页型逐尺寸看图验证。
   在做完之前, `deck_begin` / `create_slides` 传别的尺寸会被**明确拒绝**,
   不会静默画坏 (见 5605397c5 —— 静默画坏比报错糟得多)。
