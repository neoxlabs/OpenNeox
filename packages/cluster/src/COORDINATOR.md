# 协调器设计

## 核心判断：协调要劈成两半

用户提的需求（节点在干什么 / 进度汇报 / 监控埋点 / 性能 / 任务规划）里，**只有"任务规划"真的需要智能**，其余全是记账。

把记账交给 LLM 是双输：慢、贵、还会幻觉。

| | 确定性调度器（无 LLM） | 协调 Agent（LLM） |
|---|---|---|
| 就绪集计算 | ✅ | |
| 并发配额 | ✅ | |
| 进度收集与聚合 | ✅ | |
| 监控埋点 | ✅ | |
| 掉队者检测 | ✅ | |
| 持续集成（merge + verify） | ✅ | |
| 越界检测 | ✅ | |
| **初始任务规划** | | ✅ |
| **失败后重规划** | | ✅ |
| **掉队时怎么办** | | ✅ |
| **需求歧义时问用户** | | ✅ |

**证据**：
- archcompare 四结构擂台：重型协调者（官僚制）140.4s / 串行 68%，是最慢的；mission-command（轻量意图 + 满血自主）113.2s / 串行 0%
- [arXiv 2604.11378]：Coordinator 中心化模式在权衡表里的问题是"恢复靠无界的 LLM 决策"
- 我们自己：hrbench k=4 的 460 个集成错误，靠的是编译器发现的，不是靠 agent 汇报发现的

## 一、每个节点在干什么 —— 结构化，不是自然语言

### 为什么不能让节点写文字汇报

实测过：E 臂给 writer 传 15,354 字符的共享上下文，writer 的 token 从 44k 涨到 **53k** —— 它读完照样自己再读一遍代码。**自然语言在 agent 之间传递，接收方必须重新解释，成本比不传还高。**

[arXiv 2606.19135] 也指向同一条：固定 schema 协议（MCP 类）消除了 token 密集的协商；可演化 schema（Agora/ANP）的 schema 协商带来显著 token 和延迟开销。

### 所以节点状态是**观测出来的**，不是**汇报出来的**

```
节点不需要主动说 "我在写 auth 模块"
调度器从事件流里自己看：
    最近一次工具调用   → 它在干什么
    改动的文件路径     → 它在碰哪块
    turns / tokens     → 它花了多少
    上次活动时间       → 还活着吗
```

**零 token 成本，零幻觉可能，节点完全不被打断。**

节点唯一需要"主动说"的是**它自己发现的、调度器看不到的东西**：
- 遇到需要跨节点决策的歧义（`blocker`）
- 发现自己的领地划错了（`scope_conflict`）
- 完成时的结构化产出（`artifacts`）

这三类都是低频的（[arXiv 2606.19135] 实测消息密度饱和在 0.39 条/轮），且都有固定 schema。

## 二、进度汇报 —— 两条通道，职责不同

```
① 观测通道（高频，零成本，调度器 → 无 LLM）
   runtime 事件流 → NodeTelemetry
   工具调用 / token / 改动文件 / 心跳

② 上报通道（低频，固定 schema，节点 → 协调 Agent）
   blocker / scope_conflict / artifacts
   只有这三类, 不接受自由文本
```

**关键：观测通道不进 LLM 上下文。** 调度器聚合成集群快照，只在协调 Agent 需要决策时才喂给它一份摘要。否则每个节点的每次工具调用都进协调者上下文，那是灾难。

---

## 三、监控埋点 —— 埋什么由"要做什么决策"倒推

不是埋得越多越好。每个指标必须对应一个具体决策：

| 指标 | 支撑什么决策 | 实测依据 |
|---|---|---|
| **掉队者偏离度** | 要不要拆分/加援 | 墙钟 = max(节点)，掉队者决定一切。bigtask 实测同配置方差 40% |
| 并发利用率 | 配额调不调 | 集群化后并发是乘起来的，3 节点 × 3 子 agent = 12 |
| 集成错误趋势 | 集成频率够不够 | k=4 攒 19min 一次性合 → 460 错，修 25.5min（比并行段还长） |
| 越界次数 | 领地划得对不对 | k=2 出现 org/ + peopleorg/，k=4 又多出 hr/ + shared/ |
| 节点静默时长 | 是不是卡死了 | 判死按进展不按时长（core 侧同口径） |
| token/分钟 | 成本失控预警 | k=4 烧 891k token（单节点 249k 的 3.6 倍） |
| **前缀缓存命中** | 亲和性调度有没有效 | SAGA 实测 38% 时间浪费在重建 KV cache |

## 四、性能 —— 三个已量化的杠杆

### ① 掉队者（最大）

墙钟 = max(节点)。实测 k=4 四个节点 14.3 / 17.3 / 19.0 / 19.4 分钟，**最慢的决定一切**。

**调度器职责**：实时算每个节点相对同层中位数的偏离，超阈值就报给协调 Agent 决策（拆分？加援？降级？）。**检测是确定性的，处置是 LLM 的。**

### ② 进场成本

每个节点都要重新读代码库、建立理解。实测 hrbench 每节点约 250k token，其中相当部分是进场。

**调度器职责**：
- 同一节点的多轮走同一 session（前缀缓存连续）
- 派发顺序按"碰同一批文件"聚类（亲和性）

SAGA 那 38% 的 cache 浪费就是这条没做好。

### ③ 集成频率

```
攒 19min 合一次  → 460 错 → 修 25.5min（负收益）
每 3-5min 合一次 → 分歧永远只有几分钟的量
```

**调度器职责**：常开，不问 LLM。编译器不会幻觉，不需要智能决定"要不要合并"。

## 五、协调 Agent 的职责边界

它**只做判断**，不做记账。收到的是调度器聚合好的快照，不是原始事件流。

```
输入（调度器给的结构化快照）
  节点状态表 / 掉队者告警 / 集成错误摘要 / 越界告警 / 预算余量
      ↓
决策（这些确实需要智能）
  · 初始规划：目标 → 节点图（依赖 + 领地 + 切分位置）
  · 三级恢复（arXiv 2604.11378 的恢复层）
      重试 → 局部修补 → 重新规划
  · 掉队处置：拆分 / 加援 / 降级 / 就这样
  · 歧义上问：攒成一批问用户，不是逐条打断
      ↓
输出（结构化指令，调度器执行）
  add_nodes / cancel_node / respawn / replan / ask_user
```

**它不参与**：谁该跑了、还剩多少额度、要不要合并、进度怎么聚合。那些是算出来的。

---

## 六、防官僚化的三条硬约束

1. **协调 Agent 不在关键路径上** —— 节点跑的时候它是闲的。只在"有节点完成/失败/掉队"这类事件时被唤醒。它不轮询、不心跳、不"管理"。
2. **节点内部不受管** —— 给意图和领地，不给步骤。archcompare 证明重型契约钉死比 single agent 做完整个 app 还慢 2 倍。
3. **恢复是有界的** —— 三级升级各有次数上限，不是让 LLM 无限决定。这是 [arXiv 2604.11378] 权衡表里 Agent Loop 的已知弱点（unbounded recovery loops）。

## 七、待验证的假设（我不确定的部分）

| 假设 | 风险 |
|---|---|
| 协调 Agent 能规划出"低耦合"的切分 | 实测 k=2 vs k=4 差 17 倍集成代价，全看切得对不对。**它能不能判断出接口密度，我没测过** |
| 节点能识别出自己的跨节点依赖 | 460 个错误说明它们**当时没识别出来**。如果规划期也识别不出，调度器就是空壳 |
| 持续集成能把 460 压下来 | 理论支持强（CI 五十年实践），**未实测** |

**第二条是最关键的**——整个调度器建立在"依赖能被显式声明"上。要先验证它，再谈其余。
